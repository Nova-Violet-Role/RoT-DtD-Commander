### 1.1 The driver, measured

## 2. xhtml11 (67 files, 7 grammar files, 776,063 B, 21,081 lines)

Read verbatim: `dtd/xhtml11.dtd` (324 lines), `dtd/xhtml11-model-1.mod` (251), `dtd/xhtml11-flat.dtd` (4690), `dtd/xhtml-lat1.ent`, `dtd/xhtml-special.ent`, `dtd/xhtml-symbol.ent`, `dtd/VERSION`, both `xhtmlcatalog.xml`, and the head plus the full module census of `dtd/xhtml-math-svg-flat.dtd` (15,406 lines). The other 57 files are `.xsd` and were measured, not read. Census: 428 ELEMENT, 460 ATTLIST, 2838 general entities, 2979 parameter entities, 20 NOTATION, 723 conditional sections.

### 2.1 The driver, and the number that matters

`xhtml11.dtd` is 324 lines and declares 28 switches; `xhtml11-flat.dtd` is the same grammar with every module reference replaced by the module's text, 4690 lines. The ratio, 14 to 1, is the measured cost of modularity: the driver is a table of contents, the flat file is the book. The composition driver `xhtml-math-svg-flat.dtd` reaches 15,406 lines and carries three vocabularies.

Four switch shapes, all measured in this one file:

- `xhtml-inlstyle.module "INCLUDE"` wrapped in its own conditional section, the plain module switch, twenty of them.
- `xhtml-legacy.module "IGNORE"`, a module present in the tree and switched off by default. XHTML 1.1 ships the legacy elements and refuses them.
- `xhtml-bdo.module "%XHTML.bidi;"`, a switch whose value is another switch. One feature-test entity, `XHTML.bidi`, turns off both the `bdo` element and the `dir` attribute in two different modules. This is the idiom for a feature that spans modules, and it is the one the Graphic family needs for a capability like colour or time.
- `xhtml-prefw-redecl.module "IGNORE"` and its post-framework twin, the two redeclaration seams, the same pair SVG spells `svg-prefw-redecl` and `svg-postfw-redecl`.

Three declarations sit outside any switch and are load-bearing: `xhtml-model.mod` is named in the driver but instantiated by the framework, so the driver chooses the model and the framework includes it; `lang.attrib` is redeclared in the driver to add the non-namespaced `lang` beside `xml:lang`, before the attributes module reads it; `xhtml-notations.module "IGNORE"` is set in the driver with the comment "ensure XHTML Notations are disabled", which is how the corpus' 20 NOTATION declarations end up unreachable in the built grammar.

### 2.2 The framework, and what a module may not do

`xhtml-framework-1.mod` instantiates, in this order: architectural forms (IGNORE), notations (IGNORE), datatypes, XLink placeholder, qualified names, intrinsic events (IGNORE by default, INCLUDE by the driver), common attributes, the model redeclaration placeholder, the document model, and the character entities. The order is a dependency chain the comments state: events must come after datatypes and before attributes, because `Events.attrib` is folded into `Common.attrib`.

The XHTML qname module goes further than SVG's. It declares `XHTML.global.attrs.prefixed "INCLUDE"`, and every common attribute gets a second, prefixed form: `id.attrib` beside `XHTML.global.id.attrib`, `class.attrib` beside `XHTML.global.class.attrib`, collected into `XHTML.global.common.attrib`. The purpose is stated in the file: those are for use on elements in other namespaces. A grammar that will be embedded declares its attributes twice, once bare for its own elements and once prefixed for its host's.

The XSI seam is the same trick: `XHTML.xsi.attrs "INCLUDE"` declares the schema-instance namespace and `XSI.schemaLocation.attrib` so an XHTML document can carry a schema location on its root; when the switch is off, three entities collapse to empty strings.

### 2.3 The document model as a separate module

`xhtml11-model-1.mod` is the piece SVG puts in `svg11-model.mod`, at higher resolution. Three global mixes, `Inline.mix`, `Block.mix`, `Flow.mix`, built from classes: `InlStruct`, `InlPhras`, `InlPres`, `I18n`, `Anchor`, `InlSpecial`, `InlForm`, `Ruby`, and the block equivalents `BlkStruct`, `BlkPhras`, `BlkPres`, `BlkSpecial`, plus `Heading.class`, `List.class`, `Misc.class`. Three extension entities are declared for a customizer, `Misc.extra`, `Inline.extra`, `Block.extra`, and the module's own comment states the rule: each must be an OR-separated list beginning with a separator. Two derived mixes exist purely to express exclusions the DTD cannot: `InlNoAnchor.class`, everything inline except the anchor so that `a` cannot nest in `a`, and `InlNoRuby.class` with `NoRuby.content`. The DTD models an exclusion by declaring a second class without the excluded member. That is the cost, and the RelaxNG folder measures the alternative.

### 2.4 The element, measured

83 element switches and 84 attlist switches in the flat file: every element is individually switchable, and one element carries two attlist switches. Each element follows the same five-line shape as SVG's: content entity, qname entity, ELEMENT, then a separately switched ATTLIST. The Ruby module is the deepest example in the corpus of a module parameterising its own shape: `Ruby.fallback`, `Ruby.fallback.mandatory` and `Ruby.complex` are three switches selecting among three content models for the same `ruby` element, `Ruby.common.attlists` is a switch a host language turns on to give every ruby element the host's common attributes, and `NoRuby.content` defaults to text with a comment inviting the host to redefine it. A module written to be embedded declares the seams its host will use.

Modules also patch elements they do not own. The client-side image map module adds `shape` and `coords` to the anchor, and `usemap` to `img`, `input` and `object`, by a bare ATTLIST after the fact; the server-side module is nothing but two ATTLIST additions, `ismap` on `img` and `input`; the base module redeclares `head.content` to admit `base`; the events module adds focus and change handlers to nine elements. XML permits repeated ATTLIST for one element and takes the union, first declaration winning per attribute. That is the DTD's only additive mechanism, and the corpus leans on it hard.

### 2.5 The character entity sets

Three files, measured: `xhtml-lat1.ent` 96 entities (U+00A0 to U+00FF), `xhtml-special.ent` 33, `xhtml-symbol.ent` 124 (Greek, arrows, mathematical operators, geometric shapes, card suits). The `xhtml/` copies carry identical counts. Two facts worth keeping: `lt` and `amp` are declared as double character references so the entity expands to a character reference rather than to the raw character, and the symbol set is where a Suite finds `part`, `nabla`, `radic`, `infin`, `ang`, `perp`, `sdot`, `lceil`, `rfloor`, `lang`, `rang` and `loz`, the geometry vocabulary already named as entities.

### 2.6 Composition: xhtml-math-svg-flat.dtd

15,406 lines, 345 ELEMENT, 361 ATTLIST, 469 conditional sections, three vocabularies in one grammar. The mechanic, in order:

1. Three vocabulary switches, `XHTML.module`, `MATHML.module`, `SVG.module`, all INCLUDE, and three subset switches, `XHTML.Basic.module`, `SVG.Basic.module`, `SVG.Tiny.module`, all IGNORE. Turning on the tiny switch swaps the public and system identifier of the SVG DTD to the tiny driver. The subset is chosen by two entities, not by editing an include.
2. Prefixing decided per vocabulary: XHTML unprefixed, MathML unprefixed, SVG prefixed as `svg`.
3. `NS.decl.attrib` redeclared once per prefix combination inside nested conditional sections, and two combinations are declared illegal by giving the entity an empty value, with the comments "SVG and MathML are not prefixed, which is not allowed" and "SVG, MathML and XHTML are all not prefixed, which is not allowed". An invalid configuration is expressed as an empty declaration, not as an error. The grammar cannot refuse; it can only decline to declare.
4. The join: `Misc.extra` is redeclared as the MathML and SVG root classes, which is how `math` and `svg` become legal anywhere in XHTML flow, and `SVG.foreignObject.content` is redeclared to ANY, opening the other direction.

That is the whole DTD answer to composing three grammars: a switch per vocabulary, a prefix decision per vocabulary, a namespace attribute per combination, and one extension entity per direction of nesting.

## 3. xhtml (373 files, 13 grammar files, 280,396 B in the DTD family)

Read verbatim: `dtd/xhtml1-strict.dtd` (967 lines), the transitional and frameset DTDs as their measured deltas, `dtd/xhtml1.dcl`, `dtd/xhtml.soc`, `dtd/xhtmlcatalog.xml`, `description.html`, all 35 RelaxNG files (3 drivers, 29 modules, 3 exclude schemas) with `relaxng/index.html`, the NVDL dispatch rules, and the epub3 subtree's RNC modules. Census for the DTD-family files: 514 ELEMENT, 514 ATTLIST, 506 general entities, 388 parameter entities, 0 conditional sections.

### 3.1 Zero conditional sections, and why that is the point

The 8.0.0 study ranked this folder for the method rather than the switches, and the census says why: the XHTML 1.0 DTDs contain no conditional sections at all. They are the pre-modular form. Everything 1.1 expresses with switches, 1.0 expresses with parameter entities and three separate whole files. `xhtml1-strict.dtd` builds `inline` and `block` from `special`, `fontstyle`, `phrase`, `inline.forms` and `misc.inline`, then `Inline`, `Block` and `Flow` from those, and every element's content model is one of the three. Exclusions are again separate entities: `a.content` is inline minus the anchor, `pre.content` is inline minus the elements that change size, `form.content` is block minus form, `button.content` is flow minus the interactive elements.

The three profiles are three files and the deltas are measured. Transitional over strict adds the frame target, image alignment, colour and text alignment datatypes, the presentational element set (`u`, `s`, `strike`, `basefont`, `font`, `center`, `menu`, `dir`, `isindex`, `iframe`, `noframes`, `applet`), the deprecated attributes (`bgcolor`, `background`, `align`, `compact`, `noshade`, `hspace`, `vspace`), and it widens four content models, `body` from block to flow plus `noscript`, `blockquote` and `address`. Frameset over transitional is one structural change and its consequences: the root becomes head plus frameset instead of head plus body, `frameset` and `frame` are declared, a comma-separated multi-length datatype appears, and `noframes` narrows to a single body. Three files, one grammar, and the difference between two of them is a single content model.

The `html2dita/dtd` copies are the same grammars with the W3C prose comments replaced by oXygen documentation annotations, 393, 443 and 555 diff lines; the three entity files are byte-identical, diff 0. Measured hazard for this repository: the three DTDs are CRLF (966, 1189 and 1213 CR bytes) while the three entity files beside them are LF. A corpus is not uniformly encoded, and a sweep that assumes it is will report a defect that is upstream.

### 3.2 The SGML declaration, read once so it is never guessed

`xhtml1.dcl` is the SGML declaration for XML 1.0, the only file in the corpus that states parsing rules rather than a vocabulary. What it fixes, verbatim: `SHUNCHAR NONE`, `CAPACITY NONE`, `SCOPE DOCUMENT`, `NAMECASE GENERAL NO` and `ENTITY NO` so that XML is case-sensitive where SGML was not, `OMITTAG NO`, `SHORTTAG` with every minimisation off, `DATATAG NO`, `RANK NO`, `CONCUR NO`, `SUBDOC NO`, `FORMAL NO`, the five predefined entities, and `IMPLYDEF` set to NO for ATTLIST, ELEMENT and NOTATION, each marked "VALID: was YES". `VALIDITY TYPE` is likewise marked "VALID: was NOASSERT". Those four changes are what makes validation strict. The name-character tables spell out the legal characters as explicit Unicode ranges. Nothing in the Suite needs to emit this file, and everything in the Suite that says "a validating dialect" is describing exactly these settings.

`xhtml.soc` is the same binding in OASIS SOCAT form: `OVERRIDE YES`, three public-identifier lines for the profiles, three for the entity sets, and a pointer to the declaration. `xhtmlcatalog.xml` is the XML catalog form with a trap worth naming: it maps the public identifier for XHTML 1.0 Transitional twice, once to the transitional DTD and once to the strict one. A catalog can carry a contradiction and no instrument in that folder reads it.

### 3.3 RelaxNG: the same modularity without parameter entities

35 files, hand-written, and `relaxng/index.html` states outright that they were not derived from the DTDs. The mechanic differs in four ways that matter to a family designing its own grammar:

- Combination replaces redeclaration. A module extends a class with a define carrying `combine="choice"`, or an attribute pool with `combine="interleave"`. Fifteen modules extend the inline class this way. No module needs to know the others exist and inclusion order does not matter. In the DTD the same effect requires the model module to enumerate every class, which is why the DTD needs a per-profile model module and RelaxNG does not. The index page names that as the biggest difference between the two implementations.
- Include with override. The forms module includes the basic-forms module and replaces `select`; the tables module includes basic tables and replaces `table`, `th`, `td` and the three alignment pools; the frames module includes the structure module and replaces `html`. The full module is written as a diff against the basic module, which the DTD version does not do.
- Exclusions become separate schemas. Three small grammars forbid a descendant relationship: no anchor inside an anchor, no `pre` containing `img`, `object`, `applet`, `big`, `small`, `sub`, `sup`, `font` or `basefont`, no table inside a table, no form inside a form and no interactive content inside a button. Each is validated in addition to the main schema. The index page says why: XHTML Modularization partially represents these constraints by forbidding the child and not the descendant, at a substantial cost in complexity and modularity. Two grammars, each simple, instead of one grammar carrying an approximation.
- Datatypes are real. The datatypes module binds the language code, the URI and the ID family to XSD types where the DTD has CDATA and a comment.

Those idioms are what a chain grammar needs and what a DTD cannot give it: a member must be able to extend a class the root declared, without the root enumerating its members.

### 3.4 The epub3 subtree: RNC, and the extension points paying off

111 files under the epub3 folder, none of them DTD: RNC grammars, NVDL dispatch rules and Schematron. The no-namespace driver includes sixteen HTML5 modules plus datatypes, models, MathML, SVG and five epub extension modules, and its start declares the root as either the html element or an article. The combination operators are RNC's choice and interleave combines, used exactly as the XML syntax uses `combine`.

The measured payoff for the extension-point idiom is `mod/epub-svg11-30.rnc`. It includes the flat SVG RelaxNG grammar and overrides exactly five names: the start symbol, the SVG id attribute, `SVG.foreignObject.extra.content` bound to the host's flow class, `SVG.title.extra.content` bound to the host's phrasing class, and `SVG.Core.extra.attrib` extended with the epub type attribute. Four of those five are `.extra.` entities SVG declared as empty strings in 2002 and never used itself. An extension point costs one empty declaration and is worth a whole fork; this file is the proof, nine years later, in a different schema language.

Three further mechanics worth carrying:

- A vocabulary added purely by attribute. The microdata and RDFa modules add their attributes to the global pool and then declare two elements, `link` and `meta`, into new content classes. Two whole data models over one grammar, with no new element in either.
- Namespace dispatch instead of composition. The NVDL rules validate by namespace: a mode names a namespace, names the schema for it, and says attach or unwrap for everything else. Where the DTD composes three vocabularies into one grammar with prefix combinatorics, NVDL keeps three grammars and routes each subtree to its own. That is the third answer to composition in this corpus, and the cheapest.
- A profile ships a starting document. The templates folder holds sixteen files, eight pairs of document plus properties, one per profile a user can begin from: strict, transitional, 1.1 DTD, 1.1 schema, 1.1 plus MathML plus SVG, RelaxNG plus XForms, HTML5 and HTML5 article.

## 4. tei (102 files, 60 DTD files, 3,149,163 B, 55,273 lines)

Read verbatim: all 19 `-decl.dtd` modules, `core.dtd` (1030 lines) whole, `tei.dtd` (2621 lines) whole, `tei_lite.dtd` as a representative customization, and the module and element census of the remaining 21 module DTDs and 17 customizations. Census for the folder: 4494 ELEMENT, 9014 ATTLIST, 14,597 parameter entities, 614 conditional sections, 0 general entities, 0 NOTATION. The 21 `.rnc` and 21 `.rng` files beside them are the same grammar in two other languages and were measured, not read.

Measured in `tei.dtd`: 573 element-name entities, 64 datatype entities, 61 attribute classes, 590 model-class entities, 6 content macros, 19 module switches, 2 extension hooks.

### 4.1 The dual-dialect switch, the deepest use of first-declaration-binds in the corpus

```
<!ENTITY % TEI.XML 'INCLUDE' >
<![%TEI.XML;[
<!ENTITY % om.RO '' >
<!ENTITY % om.RR '' >
]]>
<!ENTITY % om.RO '- o' >
<!ENTITY % om.RR '- -' >
```

Every element declaration in every TEI module is written with that entity in the minimisation slot: `<!ELEMENT %n.abbr; %om.RR; %macro.phraseSeq;>`. With `TEI.XML` INCLUDE the entity is empty and the line is an XML element declaration. With it IGNORE the conditional section is skipped, the fallback declaration binds, and the same line becomes an SGML declaration carrying the omitted-tag indicators `- -`. One grammar, one entity, two markup dialects. The Suite has nothing at this depth and the mechanic is the general one: a syntactic slot that differs between two targets is a parameter entity, and the target is chosen once at the top.

### 4.2 Two passes, and why the module switch appears twice

Each of the 19 modules is switched by one entity, `TEI.verse`, `TEI.transcr`, `TEI.textstructure` and so on, all `IGNORE` by default, and each switch is used **twice** in `tei.dtd`: once near the top to pull in the module's `-decl.dtd`, once at the bottom to pull in its `.dtd`. The `-decl` file carries the module's attribute classes and model classes; the `.dtd` file carries its elements. Declarations first, elements second, one switch controlling both halves. That is the DTD answer to the ordering problem the XHTML framework solved with a comment about dependency order: split each module in two and run the file twice.

The two extension hooks bracket the whole thing: `TEI.extensions.ent` is referenced on line 9, before anything, and `TEI.extensions.dtd` after the classes and before the element modules. A customiser gets one seam before the vocabulary exists and one after.

### 4.3 The empty pre-declaration, and what makes a module optional

Between the switches and the class block sits a section headed "Start of pre-declared classes". It declares, as empty strings, every attribute class and every model class that a **module** would otherwise fill: `att.datable.custom.attributes`, `att.duration.w3c.attributes`, `att.global.responsibility.attributes`, `att.global.rendition.attributes`, `att.global.source.attributes`, `att.metrical.attributes`, `att.enjamb.attributes`, `att.msExcerpt.attributes`, `att.global.facs.attributes`, `att.global.change.attributes`, `att.datable.iso.attributes`, `att.duration.iso.attributes`, `att.global.linking.attributes`, `att.global.analytic.attributes`, `att.deprecated.attributes`, and the model classes of the optional modules beside them.

That block is the whole reason a TEI module can be switched off. Every name a core element might reference exists before any module runs; a module that runs replaces the empty string, a module that does not leaves it empty, and either way the element declarations parse. This is the rule the Graphic family needs stated as a law: **a grammar with an optional module declares that module's contribution as an empty entity before the module is reached, or the module is not optional.** SVG states it per module (each `.mod` opens by defaulting the attribute collections it uses); TEI states it once, centrally, for every optional module at once.

### 4.4 The x-prefix, and the five forms of every class

Every model class is declared in the generated pair

```
<!ENTITY % x.model.entryLike "" >
<!ENTITY % model.entryLike "%x.model.entryLike; %n.superEntry; |%n.entry; |%n.entryFree;">
```

A customiser redeclares only `x.model.entryLike` to prepend members, and never touches the class itself. SVG spells this `.extra.class` and applies it by hand to about thirty classes; TEI generates it for all of them.

And every class exists in **five** forms: the plain choice, plus `_sequence`, `_sequenceOptional`, `_sequenceOptionalRepeatable` and `_sequenceRepeatable`. The reason is the one structural weakness of the parameter entity: it expands textually, so a class written as `a |b |c` can be dropped into a choice group and nowhere else. A sequence needs `a, b, c` and a repeatable sequence needs `a+, b+, c+`, and the DTD has no operator to convert one into the other. So the generator emits all five. 590 model entities divided by five is 118 real classes. The 5x multiplier is the measured price of textual macro expansion, and it is the argument for a checker that reads the DTD rather than a human keeping five spellings in step.

### 4.5 Every element, four declarations

The per-element shape in `core.dtd`, measured on `abbr`:

```
<!ENTITY % abbr 'INCLUDE' >
<![ %abbr; [
<!--doc: ... -->
<!ELEMENT %n.abbr; %om.RR; %macro.phraseSeq;>
<!ATTLIST %n.abbr; xmlns CDATA "http://www.tei-c.org/ns/1.0">
<!ATTLIST %n.abbr;
 %att.global.attributes;
 %att.typed.attribute.subtype;
type %teidata.enumerated;  #IMPLIED >
]]>
```

Four things worth carrying. The element name is a parameter entity, so a customisation renames an element without forking the module. The switch is named for the element itself, not `abbr.element`, so the entity namespace is flat and a customiser writes `<!ENTITY % abbr 'IGNORE'>`. The namespace is a **defaulted attribute on every element**, which is how a namespace-unaware DTD fakes namespace membership: 573 elements, 573 `xmlns` defaults. And the attribute list is split in two, the fixed namespace one and the class-composed one, because the first is invariant and the second is what a customisation edits.

Attribute classes compose by string concatenation with multiple inheritance: `att.damaged.attributes` opens with `%att.dimensions.attributes;%att.written.attributes;` and then adds three of its own; `att.global.attributes` opens with seven other class entities and adds five. There is no inheritance operator, only juxtaposition, and it works because every class is a string.

Of the 64 datatype entities exactly one is a real enumeration, `teidata.certainty` as `(high|medium|low|unknown)`; the other 63 are `CDATA` with a name. The names carry the meaning and no validator enforces it, which is precisely the gap the RelaxNG and Schematron siblings in the same folder exist to close. Measured redundancy: the datatype block is declared twice in `tei.dtd`, once at line 591 and again at line 2440. The first binds, the second is inert, and the file is 33 declarations longer than it needs to be.

### 4.6 The customization does not use the switches

This is the finding that overturns the assumption. `grep` for the module switch names in any of the 17 shipped customizations returns nothing: `tei_lite.dtd`, `tei_ms.dtd`, `tei_svg.dtd` and the rest do not set `TEI.core` or `TEI.header`; they are whole flat grammars generated from an ODD source, each 70 KB to 224 KB, and they prune by a different means.

`tei_lite.dtd` prunes three ways, all measured against `tei.dtd`:

- **Datatypes dropped.** 25 of the 33 declared, with the ISO temporal, interval, point, prefix, sex and null-or-name types simply absent.
- **Classes emptied.** `model.entryPart`, `model.placeNamePart`, `model.placeStateLike` and their four sequence forms each declared as `""`. The class exists so that references parse, and it admits nothing.
- **Classes narrowed.** `model.resourceLike` is `"text"` where the full grammar has four members; `att.global.rendition.attributes` carries `rend` alone where the full grammar carries `rend`, `style` and `rendition`.

So the corpus' largest and most rigorous vocabulary ships a module-switch mechanism in its assembly file and does not use it in any of its own seventeen products. The products are generated flat grammars that prune by redeclaring classes to empty or to a subset. That is the DITA constraint-module philosophy arriving in TEI by a different road, and it is the second measured vote in this corpus against shipping profiles as hand-maintained driver files. The 8.0.0 study recorded that we took DITA's philosophy without seeing the other one; the correction is that TEI, the corpus' heaviest user of conditional sections, reaches the same answer for anything it actually ships.

The element counts across the seventeen, measured: `tei_bare` 18, `tei_jtei` and `tei_tite` 91, `tei_lite` 140, `tei_customization` 161, `tei_simplePrint` 166, `tei_minimal` 184, `tei_its` 185, `tei_xinclude` 187, `tei_math` 192, `tei_svg` 203, `tei_drama` 213, `tei_corpus` 266, `tei_speech` 280, `tei_enrich` 285, `tei_odds` 300, `tei_ms` 358, against `tei_all` at 573. A profile is a number between 18 and 573, and the smallest is three percent of the largest.

## 5. mathml (144 files, 71 grammar files, 1,137,954 B, 24,317 lines)

Three subtrees: `2.0/dtd` with its four entity libraries, `3.0/dtd` flattened, and `dtd/` which is not W3C MathML at all but a third-party DITA domain that embeds it. Read verbatim: `3.0/dtd/mathml3.dtd` (1633 lines), `3.0/dtd/mathml3-qname.mod` (296), `3.0/dtd/mathml2.dtd` (18), `3.0/dtd/mathml2-3.dtd` (20), `3.0/dtd/predefined.ent`, `2.0/dtd/office_mathml2.dtd` (12), `dtd/mathmlDomain2.mod` (125), `dtd/mathmlDomain2.ent` (18), and the entity libraries by measured census. ### 5.1 The eighteen-line profile, and the strongest argument in the corpus

`3.0/dtd/mathml2.dtd` is the whole of MathML 2 compatibility expressed over MathML 3, and it is eighteen lines:

```
<!ENTITY % TokenAtt "
  mathvariant CDATA  #IMPLIED
  mathsize CDATA #IMPLIED
  dir CDATA #IMPLIED
  &#x25;DeprecatedTokenAtt;">

<!ENTITY % mml3 SYSTEM "mathml3.dtd">
%mml3;

<!ATTLIST %math.qname;
  baseline CDATA #IMPLIED
  name CDATA #IMPLIED
  type CDATA #IMPLIED
>
```

Redeclare what differs, include the real grammar, add what is missing afterwards. Eighteen lines against 1633. `mathml2-3.dtd` is the same shape with two more content-model entities redeclared, twenty lines. `2.0/dtd/office_mathml2.dtd`, the OpenDocument profile, is twelve lines and changes nothing but the namespace prefix. Three profiles in this folder, none longer than twenty lines, all built by redeclare-then-include.

That is the third measured vote against hand-maintained profile drivers, and the cheapest one yet. TEI generates a whole flat grammar per profile at 70 KB to 224 KB; SVG maintains three drivers over shared modules; MathML writes eighteen lines. The difference is that MathML's profiles change only entities the base grammar already parameterised, so the profile has nothing to restate.

### 5.2 The deferred percent sign

`&#x25;DeprecatedTokenAtt;` in that file is not a typo. A parameter-entity reference written literally inside an entity value being declared would be expanded at declaration time, when `DeprecatedTokenAtt` may not exist yet. Writing the percent sign as the character reference `&#x25;` defers the expansion to the point of use. It is the DTD's only way to declare an entity whose value refers to another entity that will be declared later, and it appears twice in these eighteen lines. Any subset of ours that wants a forward reference needs exactly this.

### 5.3 A module that switches itself off

The last line of Section A of `mathml3-qname.mod`:

```
<!ENTITY % mathml-qname.module "IGNORE" >
```

with the comment "ignores subsequent instantiation of this module when used as external subset rather than module fragment. NOTE: Do not modify this parameter entity, otherwise a recursive parsing situation may result." The module sets its own switch to IGNORE on the way through, so a second attempt to include it is a no-op. Include-guard, in a DTD, with one entity. The installer inlines subsets into command files and has no such guard; this is the mechanic for one.

### 5.4 Classes named by arity, and application as a content model

MathML's content half classes its elements by **arity and domain**, not by topic: `unary-arith`, `binary-arith`, `nary-arith`, `nary-minmax`, `unary-elementary` (the twenty-four trigonometric and hyperbolic functions), `unary-veccalc` (divergence, grad, curl, laplacian), `unary-linalg` (determinant, transpose), `binary-linalg` (vectorproduct, scalarproduct, outerproduct), `nary-linalg` (selector), `nary-constructor` (vector, matrix, matrixrow), `nary-stats`, `nary-set`, `binary-set`, `nary-set-reln`, `unary-set`, `quantifier` (forall, exists), `nary-logical`, `binary-logical`, `unary-logical`, `nary-reln`, `binary-reln`, `constant-arith` (exponentiale, imaginaryi, notanumber, true, false, pi, eulergamma, infinity), `constant-set` (integers, reals, rationals, naturalnumbers, complexes, primes, emptyset).

Every one of those operator elements is declared `EMPTY` carrying only the common attributes. The operator is a token; the arguments come from the enclosing application:

```
<!ENTITY % apply.content "(%ContExp;),(%BvarQ;),(%Qualifier;)*,(%ContExp;)*">
<!ELEMENT %apply.qname; (%apply.content;)>
```

Prefix notation as a content model: first child is the operator, then bound variables, then qualifiers (`domainofapplication`, `condition`, `lowlimit`/`uplimit`, `degree`, `momentabout`, `logbase`), then operands. That is directly transferable to a geometry grammar whose verbs are constructions: a construction is an empty operator element plus its operands, classed by arity, and one `apply` shape validates all of them. Fifty-two rungs would need fifty-two empty elements and one content model, not fifty-two content models.

The geometry vocabulary MathML already names, measured in the qname module: `vector`, `matrix`, `matrixrow`, `determinant`, `transpose`, `scalarproduct`, `vectorproduct`, `outerproduct`, `divergence`, `grad`, `curl`, `laplacian`, `partialdiff`, `diff`, `int`, `interval`, `union`, `intersect`, `cartesianproduct`, `setdiff`, `subset`, `prsubset`, `card`, `mean`, `sdev`, `variance`, `median`, `mode`, and the twenty-four trigonometric functions. Trigonometry, linear algebra and vector calculus are already declared, named and classed here.

### 5.5 A datatype loosened by default, strict by redeclaration

```
<!ENTITY % MMLIDTYPE "CDATA">
<!ENTITY % MMLIDREFTYPE "CDATA">
```

with the comment that MathML 3 makes `id` CDATA so ids can repeat in different expressions in one document, and that these two "may be declared to be ID and IDREF respectively before including this DTD to match the MathML2 DTD". The strictness of a datatype is itself a parameter entity, defaulted loose. A grammar that wants both a permissive and a strict reading of the same attribute declares the type once as an entity and lets the profile choose.

### 5.6 DITA integrating MathML: specialization is a defaulted attribute

`dtd/mathmlDomain2.mod` is not W3C. It is a third-party (FIRELAB) DITA domain that embeds MathML 2, and it is the corpus' clearest statement of how DITA composes. Three moves:

1. Set the foreign vocabulary's prefix entities and include it by public identifier: `MATHML.prefixed INCLUDE`, `MATHML.prefix "mml"`, then `%mathml;`. Exactly the SVG-in-XHTML move, done by a downstream integrator rather than by a spec.
2. Declare ten new elements (`mathph`, `math`, `equation`, `eqsymbols`, `eqsymbol`, `symname`, `symdesc`, `symdescph`, `eqdefsph`, `eqdefstbl`) whose content models reference both the host's entities (`%xref;`, `%term.cnt;`, `%defn.cnt;`, `%univ-atts;`) and the guest's (`%math.qname;`).
3. Give every one of them an ancestry string as a **defaulted attribute value**:

```
<!ATTLIST equation %global-atts; class CDATA "+ topic/fig math-d/equation ">
<!ATTLIST symname  %global-atts; class CDATA "+ topic/dt math-d/symname ">
```

The leading `+` marks a domain contribution, `topic/fig` names the base element this one specialises, and `math-d/equation` names it within its own domain. A processor that understands only `topic/fig` can render `equation` correctly by reading that attribute. The specialization hierarchy is data in the instance, not structure in the grammar, which is why DITA needs almost no conditional sections: it does not switch the grammar, it labels the elements.

The companion `mathmlDomain2.ent` is eight entities long and is the whole of the domain's integration contract: `math-d-foreign`, `math-d-unknown`, `math-d-fig`, `math-d-dl`, `math-d-dlentry`, `math-d-dt`, `math-d-dd`, each naming what this domain adds to that base class, plus `math-d-att "(topic math-d)"`. A domain declares one entity per base class it extends, the shell concatenates them, and the extension is complete.

### 5.7 The entity libraries, and a name collision shipped in one tree

MathML 2 ships two complete public entity libraries under `2.0/dtd/iso8879/` and `2.0/dtd/iso9573-13/`, seventeen files each, **with the same file names**. Measured:

| file | iso8879 | iso9573-13 |
|---|---|---|
| isoamsa.ent | 56 | 146 |
| isoamsr.ent | 84 | 180 |
| isotech.ent | 62 | 161 |
| isogrk3.ent | 43 | 43 |

Library totals: 977 entities against 990. The two libraries agree where they overlap (`cularr` is U+021B6 in both) and the ISO 9573-13 set is a superset in the arrow and technical files while identical in the Greek. A catalog that resolves `isoamsa.ent` by system identifier alone gets whichever directory it happens to search, and the two answers differ by ninety declarations. That is a real trap for any tool that resolves entity sets by filename, and it is shipped inside one folder of one corpus.

MathML 3 abandons the split: `3.0/dtd` holds twenty flat `.ent` files totalling 4219 declarations, of which `htmlmathml-f.ent` alone carries 2125, and the modules are named without a library directory. The comment header on `predefined.ent` records the generation path, "produced by the XSL script entities.xsl from input data in unicode.xml" — the entity sets are generated from one Unicode table, which is why the 3.0 comments carry the Unicode character names verbatim where the 2.0 comments carry the ISO mnemonic descriptions.

### 6.1 An illegal configuration aimed at a file that is not a grammar

The driver opens with a mutually exclusive pair and then does something no other family in the corpus does:

```
<!ENTITY % sgml.features "IGNORE">
<![%sgml.features;[
<!ENTITY % xml.features "IGNORE">
]]>
<!ENTITY % xml.features "INCLUDE">

<![%sgml.features;[
<![%xml.features;[
<!-- ERROR: Exactly one of xml.features and sgml.features must be turned on! -->
<!ENTITY % dbnotn SYSTEM "http://www.oasis-open.org/docbook/xml/configerror.txt">
<!ENTITY % dbcent SYSTEM "http://www.oasis-open.org/docbook/xml/configerror.txt">
<!ENTITY % dbpool SYSTEM "http://www.oasis-open.org/docbook/xml/configerror.txt">
<!ENTITY % dbhier SYSTEM "http://www.oasis-open.org/docbook/xml/configerror.txt">
<!ENTITY % dbgenent SYSTEM "http://www.oasis-open.org/docbook/xml/configerror.txt">

<![%xml.features;[  <!ENTITY % ho "">    <!ENTITY % hh "">    ]]>
```

If both dialect switches are on, the nested conditional section fires and every module entity is redirected to a file named `configerror.txt`. The grammar cannot assert, so it aims itself at a deliberate parse failure whose filename is the diagnostic. That is stronger than the `xhtml-math-svg` approach of declaring an illegal prefix combination as an empty string, and it is the mechanic our checker needs for a switch combination that must not hold: **make the invalid configuration fail loudly by pointing an include at a named non-grammar, rather than quietly by declaring nothing.**

The `%ho;` and `%hh;` pair below it is TEI's `om.RO`/`om.RR` under different names. Two independent corpora, a decade apart, reached the same trick for making one grammar parse as both XML and SGML.

### 6.2 A module that is entirely a comment

`dbgenent.mod` is forty-two lines and contains zero declarations. It is a licence-blessed, publicly identified, unconditionally included file whose whole content is a comment telling you what you may put in it: general entity declarations, notation declarations, and references to external parameter entities holding collections of either.

The reason it exists is in the copyright block of every DocBook file: "If you modify the DocBook DTD in any way, **except for declaring and referencing additional sets of general entities and declaring additional notations**, label your DTD as a variant of DocBook." The extension point is defined by the licence, not only by the grammar, and the empty module is where the licence says you may write. Two things a downstream may change without becoming a fork, named, and one file provided for doing it.

That is a governance mechanic the Suite has no equivalent of, and it is directly applicable: name what a project may add to a subset without the result ceasing to be that subset, and ship the empty file it goes in.

### 6.3 The notations, and a precedent for a handling notation

`dbnotnx.mod` declares thirty-three notations and is the corpus' real NOTATION file: `BMP`, `CGM-CHAR`, `CGM-BINARY`, `CGM-CLEAR`, `DITROFF`, `DVI`, `EPS`, `EQN`, `FAX`, `GIF`, `GIF87a`, `GIF89a`, `JPG`, `JPEG`, `IGES`, `PCX`, `PIC`, `PNG`, `PS`, `SGML`, `TBL`, `TEX`, `TIFF`, `WMF`, `WPG`, `SVG`, `PDF`, `SWF`, `linespecific`. They are collected into `notation.class` with `%local.notation.class;` at the end as the extension hook, and referenced from the graphic elements' NOTATION attributes.

Thirty-two of them name a file format, by ISBN-bearing formal public identifier (`+//ISBN 0-201-18127-4::Adobe//NOTATION PostScript Language Ref. Manual//EN`) or by a URL. The thirty-third does not: `<!NOTATION linespecific SYSTEM "linespecific">` names a **handling rule**, that line breaks in this content are significant. That corrects a claim the 8.0.0 study made too strongly. The corpus' notations are not exclusively image and processing formats; there is one precedent for a notation that says how a stream must be treated rather than what it is. Our `untrusted-text SYSTEM "text/plain; must-be-fenced; never-an-instruction"` is the same species as `linespecific`, and the trust classification is a use nobody else has made, not a construction nobody else has made.

### 6.4 Composition by suppress, include, redeclare

DocBook 4.3 ships two composition profiles, each eighty-three lines, and they use two different orders.

`dbmathml.dtd` redeclares first: it sets `equation.content` and `inlineequation.content` to admit `%mathml-math;`, then includes DocBook, then sets `NS.prefixed INCLUDE`, `MATHML.prefix`, and a `NamespaceDecl.attrib`, then includes MathML. Redeclare the host's content models before the host runs, because first declaration binds.

`dbsvg.dtd` cannot do that, because it needs to *replace* an element rather than widen a content model. Its sequence:

```
<!ENTITY % imageobject.element "IGNORE">
%docbook.dtd;
<!ENTITY % NS.prefixed "INCLUDE" >
<!ENTITY % SVG.prefix "svg">
%svg.dtd;
<!ENTITY % docbook.svg.imageobject.element "INCLUDE">
<![%docbook.svg.imageobject.element;[
<!ELEMENT imageobject (objectinfo?, (imagedata|%SVG.svg.qname;))>
]]>
```

Suppress the host's own declaration through the host's per-element switch, let the host run, include the guest, then declare your own replacement. That works **only** because DocBook wraps every one of its 311 elements in an individually named switch. It is the strongest practical argument in the corpus for per-element switches: without them, replacing one element means forking the module that declares it.

### 6.5 Three names for one idea, and hooks for modules that do not exist

`dbpoolx.mod` declares an empty companion immediately before every class: `local.ndxterm.class`, `local.list.class`, `local.admon.class`, `local.linespecific.class`, `local.method.synop.class`, `local.synop.class`, `local.para.class`, `local.informal.class`, `local.formal.class`, `local.compound.class`, `local.genobj.class`, `local.descobj.class`, `local.xref.char.class`, `local.gen.char.class`, `local.link.char.class`, `local.tech.char.class`, `local.base.char.class`, `local.docinfo.char.class`, `local.other.char.class`, `local.inlineobj.char.class`, `local.component.mix`, and so on. Each class ends by referencing its own local entity.

So the corpus has three names for the same construct: SVG's `SVG.Shape.extra.class`, TEI's `x.model.entryLike`, DocBook's `local.list.class`. Three vocabularies, three spellings, one mechanic, and every one of them declares the extension point as an empty string beside the thing it extends. That convergence is the argument for making it a named law rather than a habit.

Beyond the local hooks, `dbpoolx.mod` declares four hooks for modules that did not exist when it was written: `forms.hook`, `forminlines.hook`, `ebnf.block.hook`, `ebnf.inline.hook`, the last two with the comment "The DocBook TC may produce an official EBNF module for DocBook. This PE provides the hook by which it can be inserted into the DTD." A grammar reserving a seam for a module that is only anticipated.

Two further devices in the same file. The redeclaration placeholders `dbpool.redecl.module` with `rdbpool`, and the driver's `intermod.redecl.module` with `rdbmods`, carry the comment "For redeclaring entities that are declared after this point while retaining their references to the entities that are declared before this point" — a seam whose position in the file is its meaning. And beside it, "Defining rdbmods here makes some buggy XML parsers happy": a workaround for a parser defect, recorded in the grammar rather than in a bug tracker.

The file also carries the matrix the DTD cannot express, as an ASCII table in a comment, showing which of ten class groups each of eleven mixtures admits, with lettered footnotes for the partial cases ("Just Procedure; not Sidebar itself or MsgSet", "Just Graphic; no other informal objects"). When a constraint cannot be declared, DocBook writes it down in a table and lets the content models approximate it.

### 6.6 Nineteen entity sets, fifty-seven conditional sections

`dbcentx.mod` handles nineteen ISO entity sets and does so three times over: once declaring each as a bare public identifier under `sgml.features`, once as a public identifier plus a system file under `xml.features`, and once again in a closing block of nineteen conditional sections that actually reference them. Three passes, fifty-seven conditional sections, nineteen entity sets, and the whole apparatus exists so the same module works in both dialects.

The file names drifted between versions: 4.2 and 4.3 ship `ent/iso-amsa.ent` at 64 lines, 4.4 and 4.5 ship `ent/isoamsa.ent` at 98. Same public identifier, different filename, different content. Together with the MathML `iso8879` against `iso9573-13` split, that is the second measured instance in this corpus of one entity-set name resolving to different files with different contents.

### 6.7 The arc, and where it ends

DocBook 5.0's `dtd/docbook.dtd` is 4200 lines and has no modules, no conditional sections, and no class entities except two attribute pools, `db.common.attributes` and `db.common.linking.attributes`. Every content model is written out in full: the alternation for `title` runs to more than a hundred element names and is repeated verbatim for `titleabbrev` and for `subtitle`. Beside it in the same directory sit `rng/`, `sch/`, `xsd/`, `docbook.nvdl`, `catalog.xml` and `tools/`. The DTD is a generated artifact; the RelaxNG is the source.

DocBook 5.1 ships `catalog.xml`, `docbook.nvdl`, `rng/`, `sch/` and `tools/`. There is no `dtd/` directory at all.

That is the arc of the whole corpus in one folder. SVG, XHTML 1.1, TEI and DocBook 4 each built an elaborate DTD module system; DocBook 5.0 generates the DTD from a RelaxNG source; DocBook 5.1 stops shipping one. XHTML tells the same story in a different order, with a hand-written RelaxNG implementation beside the DTD and an epub3 successor written entirely in RNC. TEI ships `.rnc` and `.rng` beside every `.dtd`.

The honest reading, and it belongs in the record: the mechanics this study is borrowing are the mature form of a language most of its own authors have since left, and they left for reasons that are visible in the files — RelaxNG expresses exclusions, real datatypes and co-occurrence constraints that a DTD can only approximate with a second class, a comment, or a separate schema. None of those three reasons applies to the Suite, because our subsets declare the shape of a **prompt** and are read by a model and by our own checkers, not used to validate a document stream against a datatype library. What the corpus proves is that the module, the switch, the empty extension point and the redeclare-then-include profile are sound at scales from eighteen lines to fifteen thousand. What it does not prove is that a DTD is the right validator for documents, and nothing in the Suite claims that.

## 7. JATS-DTDs (98 files, 90 grammar files, 2,126,385 B, 41,445 lines)

Five drivers (three JATS article profiles, two BITS book profiles), 81 `.ent` modules, an embedded MathML 3 and two XHTML modules, four entity-set directories, and two catalogs. Read verbatim: `JATS-journalpublishing1-mathml3.dtd` (861 lines) whole, the four `journalpubcustom-*` files, `JATS-default-classes1.ent`, `JATS-default-mixes1.ent`, `JATS-common-atts1.ent`, `JATS-notat1.ent`, and the declaration census of all 81 modules. Folder census: 556 ELEMENT, 545 ATTLIST, 2204 general entities, 1789 parameter entities, 10 NOTATION, 27 conditional sections.

### 7.1 Zero switches, and the order that is the mechanism

Measured across all five drivers: `condsect=0`. Not one conditional section in any JATS or BITS driver, and 27 in the whole folder against SVG's 407 and DocBook's 5057. The suite composes entirely by declaring before including, and the driver carries only 12 to 18 parameter-entity references and 4 to 7 element declarations. Everything else is in the modules.

The sequence is fixed and the driver says so: "Note: These modules must be called after all Module of Modules but before any other modules. Unlike any other grouping, **order of these modules matters.**" The order, verbatim from the file:

1. `%journalpubcustom-modules.ent;` and `%modules.ent;` — declare the module names
2. `%JATS-ali-namespace.ent;`, `%JATS-common-atts.ent;`
3. `%journalpubcustom-classes.ent;` then `%default-classes.ent;`
4. `%journalpubcustom-mixes.ent;` then `%default-mixes.ent;`
5. `%journalpubcustom-models.ent;`
6. `%common.ent;`, then the fourteen content modules
7. MathML setup, XHTML table setup, character entities, notations

**Every default module is preceded by its custom counterpart.** First declaration binds, so the custom file wins for each entity it names and the default file fills in the rest. That is the entire override mechanism: pair each shared module with a profile module and call the profile one first. No switch, no IGNORE, no redeclaration placeholder.

Measured, the profile is small. `journalpubcustom-classes1.ent` declares 9 entities against `default-classes1.ent`'s 102. `journalpubcustom-mixes1.ent` declares 3 against `default-mixes1.ent`'s 11. `journalpubcustom-models1.ent` declares 56. Sixty-eight redeclarations govern a suite carrying 1324 parameter entities and 325 elements: a profile is about five percent of the grammar it profiles.

### 7.2 Declaring a module and invoking it are different files

`JATS-modules1.ent` holds 34 declarations and invokes nothing. Its own comment: "Since this module declares but does not invoke modules, this DTD invokes any modules it uses by referencing the external Parameter Entities defined in the Module of Modules." The driver then reads as a list of one-line invocations, `%articlemeta.ent;`, `%backmatter.ent;`, `%display.ent;`, `%format.ent;`, `%funding.ent;`, and the file stays legible at 861 lines with a 300-line comment header.

There are two such files per profile: the suite's `modules.ent` for shared modules, and the profile's `journalpubcustom-modules.ent` naming only the four files unique to that profile. Separating the name from the use is what lets a profile add a module without touching the suite.

### 7.3 An extension point deliberately made coarse

From `journalpubcustom-mixes1.ent`, on the pair `just-rendition` and `rendition-plus`:

> MAINTENANCE NOTE: This Parameter Entity and the related PE "rendition-plus" have been put in place to **restrict the amount of variability that a person modifying the DTD through PE redefinition can achieve**. Some elements have been set #PCDATA plus one PE and some have been set to #PCDATA plus the other in an effort to allow designers to modify entire groups of elements, but not to change similar models individually.

And `just-rendition` is then declared as the empty string.

That is the opposite design position from TEI, which gives every one of 118 classes its own `x.` hook and every element its own switch. JATS decides on purpose that a customiser may move a whole group or nothing, and shapes the entity graph so that finer changes are not expressible. **The granularity of the extension points is the granularity of the variation the maintainer is willing to support**, and it is a decision, not an accident. For the Suite this is the argument that `preview.content` and `ask.rounds` being raisable while other entities are not is a position to state, not an omission to fix.

### 7.4 Governance as two required sentences

DocBook says label your variant. JATS names the two claims a downstream may make and requires one of them in every module:

> 1. If you create a DTD from the JATS DTD Suite and intend to stay compatible with the suite, then please include the following statement as a comment in all of your DTD modules: "Created from, and fully compatible with, the ANSI/NISO Z39.96 Journal Article Tag Suite (JATS)."
> 2. If you alter one or more modules of the suite, then please rename your version and all its modules to avoid any confusion with the original suite. Also, please include: "Based in part on, but not fully compatible with, the ANSI/NISO Z39.96 Journal Article Tag Suite (JATS)."

with "Do not modify the suite directly or redistribute modified versions of the suite" above it. Two named compatibility claims, one required statement each, and a rename obligation attached to the second. That is the most complete governance statement in the corpus and it costs two sentences.

### 7.5 The entity collision, solved by partition

MathML ships `isoamsa.ent` twice with different contents in `iso8879/` and `iso9573-13/`. JATS ships the same standards' entity sets in four directories with **no filename appearing twice**:

| directory | files |
|---|---|
| `iso8879/` | isobox, isocyr1, isocyr2, isodia, isolat1, isolat2, isonum, isopub |
| `iso9573-13/` | isoamsa, isoamsb, isoamsc, isoamsn, isoamso, isoamsr, isogrk3, isomfrk, isomopf, isomscr, isotech |
| `mathml/` | mmlalias, mmlextra |
| `xmlchars/` | isogrk1, isogrk2, isogrk4 |

Each set is filed under the standard that actually defines it: `isogrk3` is in ISO 9573-13 and lives there, `isogrk1`, `isogrk2` and `isogrk4` are not and live in `xmlchars/`. Partition by provenance, and the collision cannot occur. That is the corrective to the trap recorded in section 5.7, measured in the same corpus.

Two catalogs ship beside them, `catalog-jats-v1-1-no-base.xml` and `catalog-jats-v1-1-with-base.xml`, 110 entries each, differing only in whether they carry `xml:base`. The same mapping shipped twice for two resolver behaviours rather than one mapping that works in neither.

### 7.6 Ten notations, four of them the same one

```
<!NOTATION LaTeX PUBLIC ...
<!NOTATION TEX   PUBLIC ...
<!NOTATION tex   PUBLIC ...
<!NOTATION TeX   PUBLIC ...
<!NOTATION cgmchar / cgmclear / gif / eps / jpeg / tiff
```

Four spellings of one notation, declared separately because XML names are case-sensitive and authors type all four. A grammar absorbing author variation by declaring every casing it expects to see. The rest name image formats, consistent with DocBook and with the 8.0.0 finding.

`JATS-common-atts1.ent` shows the same duplication under pressure: `jats-common-atts` and `jats-common-atts-id-required` are the same pool differing only in `id ID #IMPLIED` against `id ID #REQUIRED`, and the change history records that the two "are kept in sync" by hand. The defaulting keyword is the one part of an attribute declaration a parameter entity is not usually used to parameterise, and the cost is a second entity maintained manually.

### 7.7 What the suite costs in comment

Measured declaration density: `journalpubcustom-classes1.ent` 9 declarations in 337 lines, `journalpubcustom-mixes1.ent` 3 in 258, `journalpubcustom-modules1.ent` 4 in 261, `JATS-notat1.ent` 10 in 269. Every file carries the same ninety-line provenance header plus a numbered change history running back to 2002. The folder is 2.1 MB of file for 325 elements and 1324 parameter entities.

That is the far end of self-documentation, and it is worth naming as a cost rather than a virtue: the ratio makes the suite readable by a human opening any single file cold, and makes it nearly unreadable in aggregate. Our own subsets sit at the other end, and the corpus does not settle which is right; it shows both extremes shipping.

## 8. org.oasis-open.dita.v1_3 (656 files, 159 grammar files, 1,743,772 B, 41,497 lines)

Counted with `find`: 34 `.dtd`, 55 `.mod`, 70 `.ent`, plus 310 `.xsd`, 146 `.rng`, 38 `.xml`, 1 `.zip`, 1 `.txt`, 1 `.dita`. Of the 159 grammar files, 29 are DITA's own shells (27 document types plus two foreign-vocabulary drivers), 47 are DITA `.ent` files and 54 are DITA `.mod` files; the remaining 29 are borrowed whole — the MathML 3 entity sets and drivers under `technicalContent/dtd/mathml/mathml3/` (23 `.ent`, 1 `.mod`, 3 `.dtd`), the flat SVG 1.1 under `technicalContent/dtd/svg/svg11/`, and one `relaxng.dtd` under the RelaxNG tree.

DITA's own 130 grammar files: **623 `<!ELEMENT`, 1235 `<!ATTLIST`, 3178 `<!ENTITY`, 0 `<!NOTATION`**.

### 8.1 Zero conditional sections — the finding that separates DITA from half the corpus

Four files in the whole tree contain the token `<![`, and all four are borrowed:

```
./technicalContent/dtd/mathml/mathml3/mathml3-qname.mod
./technicalContent/dtd/mathml/mathml3/mathml3.dtd
./technicalContent/dtd/mathml/mathml3-ditadriver.dtd
./technicalContent/dtd/svg/svg11/svg11-flat-20110816.dtd
```

The third is DITA's own file but it is a copy of MathML's namespace block, kept only so the driver can redeclare `NamespaceDecl.attrib`. **Not one of DITA's 130 grammar files uses a marked section for configuration.** Every configuration decision in DITA is a *redeclaration before an include*, and nothing else.

Set against the families already read:

| family | module switches | mechanism |
|---|---|---|
| svg 1.1 | 34 | `<!ENTITY % X.module "INCLUDE">` + `<![%X.module;[ … ]]>` |
| xhtml11 | 28 | same, plus a switch whose value is another switch |
| tei | 19, each used twice | same |
| docbook 4.5 | many, plus a poisoned include for the illegal configuration | same |
| JATS | 0 | ordered redeclaration (custom-classes before default-classes) |
| **dita 1.3** | **0** | **ordered redeclaration in a shell, first-declaration-binds** |

Two of the seven families ship no switch at all, and both are the two most heavily *specialised* vocabularies in the corpus. That is not a coincidence to note in passing: a switch answers "is this module present?", and both JATS and DITA replaced that question with "what does this name expand to?", which is strictly more expressive — a redeclaration can add, replace, narrow, or empty, where a switch can only include or ignore.

### 8.2 The shell: sixteen named sections in a fixed order

`task.dtd` is 343 lines, 13,177 B. Its comment banners, in file order, are the whole architecture:

```
TOPIC ENTITY DECLARATIONS
DOMAIN CONSTRAINT INTEGRATION
DOMAIN ENTITY DECLARATIONS
DOMAIN ATTRIBUTES DECLARATIONS
DOMAIN EXTENSIONS
DOMAIN ATTRIBUTE EXTENSIONS
TOPIC NESTING OVERRIDE
DOMAINS ATTRIBUTE OVERRIDE
CONTENT CONSTRAINT INTEGRATION
TOPIC ELEMENT INTEGRATION
DOMAIN ELEMENT INTEGRATION
```

Every declaration a shell makes precedes every `.mod` it includes, because first-declaration-binds is the only mechanism in play. `topic.dtd` (324 lines, 12,584 B) is the same file with the task-specific members removed; `generalTask.dtd` is 333 lines; `ditabase.dtd`, the shell that admits every type at once, is 433 lines. Four shells differing by under 25 % in size, and the difference is entirely *which names they redeclare*.

DOMAIN EXTENSIONS is one redeclaration per extended base element:

```
<!ENTITY % foreign "foreign |
                         %svg-d-foreign; |
                         %mathml-d-foreign;
                        ">
```

The base element's own name leads the list, so a domain always *widens* — a shell that includes no domain still gets `foreign`.

### 8.3 A domain is an `.ent` / `.mod` pair, and the `.ent` is four lines of content

`highlightDomain.ent`, stripped of its header, is two declarations:

```
<!ENTITY % hi-d-ph
  "b | i | line-through | overline | sup | sub | tt | u" >

<!ENTITY hi-d-att
  "(topic hi-d)" >
```

One parameter entity naming what the domain contributes, one **general** entity naming the domain itself. `highlightDomain.mod` then declares the eight elements, each with a `.content` and a `.attributes` parameter entity, and closes with the specialization block:

```
<!ATTLIST  b %global-atts;  class CDATA "+ topic/ph hi-d/b "  >
<!ATTLIST  i %global-atts;  class CDATA "+ topic/ph hi-d/i "  >
```

The split is functional, not cosmetic: the `.ent` is read by the *shell*, before anything, so the shell can wire the domain into base-element models; the `.mod` is read last, when every name it references is already bound. Fifteen domains ship this way in DITA 1.3 base + technicalContent alone.

`deliveryTargetAttDomain.ent` is the exception that names the rule — an **attribute** domain, so it ships an `.ent` with **no `.mod`**, because it declares no element:

```
<!ENTITY % deliveryTargetAtt-d-attribute
  "deliveryTarget CDATA #IMPLIED" >

<!ENTITY deliveryTargetAtt-d-att
  "a(props deliveryTarget)" >
```

The domain entity is `a(props deliveryTarget)` where the element domain's was `(topic hi-d)`. The leading `a(` is the whole distinction between an attribute domain and an element domain, carried in a string a validating parser never inspects. (Read: both files verbatim. Reasoned: that the `a(` prefix is the discriminator — the DTD cannot enforce it, so this is a convention the *processor* reads.)

### 8.4 The instance carries its own grammar's configuration

`topic.mod` declares a default and the shell overrides it:

```
<!-- topic.mod, DOMAINS ATTRIBUTE OVERRIDE -->
<!ENTITY included-domains "" >
```

```
<!-- task.dtd, DOMAINS ATTRIBUTE OVERRIDE -->
<!ENTITY included-domains
 "&task-att;
  &abbrev-d-att;
  &deliveryTargetAtt-d-att;
  &equation-d-att;
  &hazard-d-att;
  &hi-d-att;
  &indexing-d-att;
  &markup-d-att;
  &mathml-d-att;
  &pr-d-att;
  &relmgmt-d-att;
  &sw-d-att;
  &svg-d-att;
  &ui-d-att;
  &ut-d-att;
  &xml-d-att;
  &taskbody-constraints;
  " >
```

and `topic.mod` spends it in the root element's attribute list:

```
<!ELEMENT  topic %topic.content;>
<!ATTLIST  topic %topic.attributes;
                 %arch-atts;
                 domains CDATA "&included-domains;" >
```

A **general** entity reference inside an attribute default. Every conforming `topic` element in every instance therefore carries a `domains` attribute listing exactly the domains and constraints its grammar was assembled from — sixteen strings for `task.dtd`, the empty string for a bare topic. A processor holding only the instance, with no access to the DTD, still knows the configuration, because the configuration was *stamped into the data at parse time*.

The same technique stamps the version:

```
<!ENTITY % DITAArchNSPrefix "ditaarch" >
<!ENTITY % arch-atts
             "xmlns:%DITAArchNSPrefix; CDATA #FIXED 'http://dita.oasis-open.org/architecture/2005/'
              %DITAArchNSPrefix;:DITAArchVersion CDATA '1.3' " >
```

`1.3` is written once, in the grammar, and appears on every root element of every document by defaulting. **No author ever types the version.** That is our own release law — `lib/amplify.mjs recognize` computes the version and `checker/release-notes.mjs --versions` refuses a manifest that disagrees — arrived at independently and shipped by OASIS in 2005. It is the strongest precedent in the corpus for the rule, and worth citing in the 9.0.0 notes rather than presenting the rule as ours alone.

The namespace prefix is a parameter entity carrying the comment "can be overridden through predefinition in the document type shell" — so even the *prefix* of the architecture attribute is a shell decision, the same technique SVG uses for `SVG.prefix` (§1) and MathML for `MATHML.prefix` (§5).

### 8.5 `class`: ancestry as a defaulted attribute, with significant whitespace

```
<!ATTLIST  topic     %global-atts;  class CDATA "- topic/topic "     >
<!ATTLIST  section   %global-atts;  class CDATA "- topic/section "   >
<!ATTLIST  b         %global-atts;  class CDATA "+ topic/ph hi-d/b " >
```

`-` for a structural type, `+` for a domain. Every value opens with a sigil and a space and closes with a space, so a processor asking "is this a `topic/ph`?" does a substring test for `" topic/ph "` and cannot false-positive on `topic/phrase`. The delimiter discipline is the whole safety of the scheme, and it lives in trailing spaces inside a CDATA default — invisible in any editor that trims.

That is a hazard worth naming for our own work: this repository's encoding rule strips trailing whitespace on every write. A DITA-style ancestry attribute written under our rules would be silently corrupted by our own tooling. If the Graphic suite adopts an ancestry string, it must use an explicit delimiter that survives trimming, not a space.

### 8.6 A constraint is a redeclaration that narrows, and it advertises itself

`strictTaskbodyConstraint.mod`, whole, minus the header:

```
<!ENTITY taskbody-constraints "(topic task strictTaskbody-c)" >
<!ENTITY % prereq "prereq">
<!ENTITY % context "context">
<!ENTITY % steps "steps">
<!ENTITY % steps-unordered "steps-unordered">
<!ENTITY % result "result">
<!ENTITY % tasktroubleshooting "tasktroubleshooting">
<!ENTITY % example "example">
<!ENTITY % postreq "postreq">
<!ENTITY % taskbody.content
              "((%prereq;)?, (%context;)?, (%steps; | %steps-unordered;)?,
                (%result;)?, (%tasktroubleshooting;)?, (%example;)?, (%postreq;)?)" >
```

It declares no element and no attribute. It binds `taskbody.content` before `task.mod` can, so the general form loses to the strict sequence. And it declares a general entity `taskbody-constraints` in exactly the shape a domain entity takes, which is why `task.dtd` can list `&taskbody-constraints;` as the last member of `included-domains` — a constraint is advertised in the instance beside the domains, by the same mechanism.

`learningNoLearning1Constraint.mod` shows the other direction:

```
<!ENTITY lcInteractionNoLearning1-constraint-constraints
  "(topic lcInteraction learningNoLearning1-c)" >
<!ENTITY % lcInteractionBase2 "lcInteractionBase2">
<!ENTITY % lcInteractionBase "" >
<!ENTITY % lcInteraction.content "(%lcInteractionBase2;)*" >
```

`<!ENTITY % lcInteractionBase "">` — an extension point **emptied**. SVG, TEI and DocBook declare an extension entity empty so a customization can fill it (§1, §4, §6); DITA fills it in the base module and lets a constraint empty it. Same mechanism, opposite polarity, and the pair together is the general statement: *an empty parameter entity is a seam, and first-declaration-binds decides which side of the seam wins.*

Five constraint modules ship in 1.3: `strictTaskbodyConstraint.mod`, `machineryTaskbodyConstraint.mod`, `learningNoLearning1Constraint.mod`, `learningNoLearning2Constraint.mod`, `learningAggregationsTopicrefConstraint.mod`.

### 8.7 Foreign vocabularies: an 18-line driver and a suppression

`svg11-ditadriver.dtd` is 18 lines — set `NS.prefixed` INCLUDE, set `SVG.prefix` to `svg`, include the flat SVG. `mathml3-ditadriver.dtd` copies MathML's namespace block so it can redeclare `NamespaceDecl.attrib`, and adds one line the whole corpus should be read against:

```
<!ENTITY % mathml-charent.module "IGNORE" >
```

with the comment "DITA-specific: Don't allow use of general text entities. DITA documents should not have any general text entity references."

DITA imports MathML and switches off the 23 ISO entity sets it ships with. The reason is a trust boundary: a general entity reference in an instance is content the parser expands from a source the document type controls, and DITA's processing model wants no such expansion. It is the only place in the corpus where a family imports a vocabulary and *removes a capability from it on the way in* — DocBook's `dbsvg.dtd` (§6) suppresses one of its own elements to make room, which is the mirror case, not the same one.

This is directly load-bearing for us. `cc-core.dtd` classifies trust with NDATA channels and a `#FIXED` attribute; DITA reaches the same boundary by refusing the expansion mechanism outright. Both are defensible; ours is finer-grained, theirs is unfalsifiable. Recording it because the 9.0.0 chain grammar must decide the same question — whether a band's artifact, handed on as the next band's user-args, may carry an entity reference at all.

### 8.8 `ditaval.dtd`: the control file opts out of the architecture

4,447 B, and after the header it is nine declarations of plain XML:

```
<!ELEMENT val (style-conflict?, (prop | revprop)*)>
<!ELEMENT style-conflict EMPTY>
<!ATTLIST style-conflict
  foreground-conflict-color CDATA #IMPLIED
  background-conflict-color CDATA #IMPLIED >
<!ELEMENT prop (startflag?, endflag?)>
<!ATTLIST prop
  att CDATA #IMPLIED
  val CDATA #IMPLIED
  action (flag|include|exclude|passthrough)  #REQUIRED
  … >
```

No parameter entity. No `class`. No `domains`. No architecture attributes. No specialization. No module. The one file in the family that describes *how the family is processed* is written in the flattest DTD in the tree, and its only enumeration — `(flag|include|exclude|passthrough)` — is a real enumerated attribute where the content vocabulary uses CDATA everywhere.

The lesson is the one we need for `cc-chain.dtd`: a grammar that describes control is not a grammar that describes content, and trying to make the control language extensible buys nothing, because nobody specialises a build file. DITA had every tool for extensibility loaded and deliberately used none of them here. Our chain grammar should be enumerations and required attributes — a declared root, one intake, one gate, `--no-gate` as a token — not a parameterised module.

### 8.9 What DITA 1.3 contributes to 9.0.0

1. **Configuration by redeclaration alone.** 0 conditional sections in 130 grammar files. A switch is not required to build a configurable grammar, and dropping it removes the `configerror.txt` class of problem DocBook needed (§6) — an illegal configuration in DITA is a name that expands to nothing, which fails at the point of use rather than needing a poisoned include.
2. **The version is stamped by the grammar, never typed.** `DITAArchVersion CDATA '1.3'` on every root element by defaulting. Precedent for our release law; cite it.
3. **The instance carries its own configuration.** `domains CDATA "&included-domains;"` — a general entity reference expanded into an attribute default. The mechanism for a chained artifact to declare which bands produced it without the next band having to re-derive it.
4. **Constraint modules are the fourth operation on a seam.** Add (domain), replace (profile), narrow (constraint), empty (`""`). Our subsets have used the first two; the geometry family will need the third and fourth if the Graphic suite is to generalise without forking.
5. **Trailing whitespace can be semantic.** `class CDATA "- topic/topic "` is a hazard against our own encoding rule. Any ancestry string we ship must be delimited by a character that survives trimming.
6. **The control language is flat on purpose.** `ditaval.dtd` — 9 declarations, no parameter entities, one real enumeration. The shape `cc-chain.dtd` should take.

### 9.1 `org.lwdita` ships no grammar at all

Named in the brief's SOURCE list beside the other DITA folders. Measured contents: 33 `.jar`, 32 `.xsl`, 6 `.xml`, 3 `.txt`, a `LICENSE` and a `NOTICES`, under `org.lwdita/lib` and `org.lwdita/xsl`. It is the DITA Open Toolkit **plugin** that processes Lightweight DITA — the transform, not the vocabulary. The vocabulary is `org.oasis-open.xdita.v0_2_2`.

Recorded rather than skipped, because the corpus study's method is a census: a folder that contributes zero grammar files is a measurement, and reporting it as studied without saying it is empty of DTDs would be the exact defect §0 forbids.

### 9.2 Three major versions, and not one grammar file renamed

Comparing grammar-file basenames:

```
1.1 -> 1.2   only in 1.1: (none)      shared: 36 of 36
1.2 -> 1.3   only in 1.2: (none)      shared: 97      added in 1.3: 62
```

Every `.dtd`, `.mod` and `.ent` name in DITA 1.1 (November 2006) still exists in 1.2, and every name in 1.2 still exists in 1.3 (January 2018). Across twelve years and two major versions, **the suite grew only by addition**. The 62 files 1.3 adds are the MathML 3 import (28 files), the SVG import (2), and thirteen genuinely new domains and types — `troubleshooting`, `markupDomain`, `mathmlDomain`, `svgDomain`, `xmlDomain`, `equationDomain`, `releaseManagementDomain`, `ditavalrefDomain`, `deliveryTargetAttDomain`, `learningGroupMap`, `learningObjectMap`, `learning2Domain`, `learningInteractionBase2Domain` — plus three constraint modules.

That is `cc-record.dtd`'s LAW.REC.2 (`since` never decreases as the field number grows) enforced by a standards committee at file granularity, with a public identifier as the field number. It is the strongest external evidence in the corpus that append-only is a workable discipline over a decade, not just a rule we asserted.

**The claim is exact at file level and not at declaration level.** `topic.mod` between 1.2 and 1.3 differs by three parameter-entity names:

```
removed in 1.3:  <!ENTITY % date-format
added in 1.3:    <!ENTITY % shortdesc.attributes
                 <!ENTITY % shortdesc.content
```

One removal in a 700-line module across a major version. The `.content` / `.attributes` pair added for `shortdesc` is the 1.2 refactor (`2008.02.13 RDA: Create .content and .attributes entities`) finally reaching the last element that lacked it. So: files are append-only, declarations are nearly so, and the one deletion is a name nothing else referenced.

### 9.3 DITA 1.1 already had the whole architecture, and wrote down why the order matters

`org.dita.specialization.dita11/dtd/topic.dtd` is 171 lines, 8,102 B, dated November 2006. Its banners:

```
DOMAIN ENTITY DECLARATIONS
DOMAIN ATTRIBUTE DECLARATIONS
DOMAIN EXTENSIONS
DOMAIN ATTRIBUTE EXTENSIONS
TOPIC NESTING OVERRIDE
DOMAINS ATTRIBUTE OVERRIDE
TOPIC ELEMENT INTEGRATION
DOMAIN ELEMENT INTEGRATION
```

Eight of the eleven sections §8.2 measured in 1.3's `task.dtd`. The three missing are `DOMAIN CONSTRAINT INTEGRATION`, `CONTENT CONSTRAINT INTEGRATION` and `DOMAIN ATTRIBUTES DECLARATIONS` — constraints did not exist yet. Measured: 0 constraint modules in 1.1, 2 in 1.2 (`strictTaskbodyConstraint.mod`, `machineryTaskbodyConstraint.mod`), 5 in 1.3.

The 1.1 shell carries the rationale for the whole architecture in a comment above `included-domains`:

```
<!-- Must be declared ahead of the DTDs, which
                        puts @domains first in order -->
```

First-declaration-binds, stated in the file, in 2006. And in `DOMAIN EXTENSIONS`:

```
<!-- One for each extended base element, with
                        the name of the domain(s) in which the
                        extension was declared -->
<!ENTITY % ph "ph | %pr-d-ph; | %sw-d-ph; |
                                    %hi-d-ph; | %ui-d-ph;" >
```

and the two empty seams:

```
<!ENTITY % props-attribute-extensions  "" >
<!ENTITY % base-attribute-extensions "" >
```

`concept.mod` logs the change that matters most to us:

```
<!-- 2006.11.30 RDA: Remove #FIXED from DITAArchVersion -->
```

The architecture version had been `#FIXED` and was deliberately loosened to a plain default. §8.4 read the version stamp as precedent for our "the version is never typed" law; this is the honest counterweight. OASIS decided an instance must be *allowed* to carry a version its grammar did not supply, because a document outlives the DTD that validated it. Our law is stricter than theirs — `checker/release-notes.mjs --versions` refuses a disagreement outright — and that strictness is a choice we are making with the precedent in view, not in ignorance of it.

### 9.4 XDITA: the extension seam shipped as commented-out template lines

Five grammar files, 45,248 B: `lw-topic.dtd` (109 lines), `lw-map.dtd` (107), `lw-topic.mod` (492, 37 elements), `lw-map.mod` (214, 11 elements), `lw-highlightDomain.mod` (79, 5 elements). Fifty-three elements against DITA 1.3's 623.

`lw-topic.dtd` keeps the shell shape but replaces the domain-entity block with a literal:

```
<!ENTITY included-domains "(topic hi-d) (topic h5m-d)" >
```

— the domain strings typed out rather than assembled from `&hi-d-att;`, because with two domains the indirection buys nothing.

The section that matters is `REMOVE ATTRIBUTE/ELEMENT GROUPS`:

```
<!-- Remove a group by uncommenting its redefinition below -->

<!--ENTITY % filters " " -->
<!--ENTITY % reuse " " -->
<!--ENTITY % variable-content " " -->
<!--ENTITY % variable-links " " -->
<!--ENTITY % localization " " -->
<!--ENTITY % nested-blocks "p" -->

<!--For each group removed add a corresponding constraint value to
    the excluded-domains entity. The constraint name should be "no-"
    followed by the name of the entity removed/constrained.
    For example, if you removed reuse attributes, add the value
    "no-reuse-c" to the excluded-domains entity definition-->

<!ENTITY excluded-domains " " >
```

Every constraint the shell supports is present **as an inert comment the user uncomments**. SVG, TEI and DocBook publish an empty extension entity and leave the author to discover its name from documentation; XDITA writes the redeclaration itself, commented out, with the naming convention for the resulting constraint spelled out in prose beside it. The discovery problem is solved by putting the answer in the file.

That is directly transferable. Our `create-prompt-<schematic>-dtd` family generates a schematic the user then edits; shipping the customization points as commented-out declarations — with the law that governs each — would make a generated subset self-teaching in exactly this way, at the cost of nothing but bytes.

### 9.5 A dead declaration in shipped OASIS grammar

`excluded-domains` is declared in both XDITA shells, documented in four lines of prose, and **referenced nowhere**. Grepped across all five grammar files:

```
lw-map.dtd:84:   <!ENTITY excluded-domains " " >
lw-topic.dtd:83: <!ENTITY excluded-domains " " >
```

Two declarations, zero uses. The attribute default that would have spent it reads:

```
<!ATTLIST topic
             id ID #REQUIRED
             xmlns:ditaarch CDATA #FIXED "http://dita.oasis-open.org/architecture/2005/"
             ditaarch:DITAArchVersion CDATA "1.3"
             domains CDATA "&xdita-constraint; &included-domains;"
             outputclass  CDATA #IMPLIED
             %localization;
             class CDATA "- topic/topic ">
```

`&xdita-constraint;` and `&included-domains;` are both expanded; `&excluded-domains;` is not, in either `lw-topic.mod` or `lw-map.mod`. A general entity a DTD declares and never references is expanded by nothing and reaches no instance. The negative-list mechanism was designed, documented with a naming convention, shipped in 2014, and carried through seven logged updates to July 2017 without ever being wired.

This is the exact defect class `dtd-contract-auditor` exists to find — a declaration nothing uses — occurring in a committee-reviewed OASIS deliverable. Two conclusions, and the second is the useful one:

1. The audit is not paranoia. Orphan declarations survive review in the best-resourced grammar work in the corpus.
2. **An orphan is invisible precisely because a DTD cannot fail on it.** Nothing a validating parser does will ever notice. The only instrument that finds it is a census of declarations against references — which is a program, not a schema. Our audit must therefore stay a program, and the 9.0.0 chain grammar must not be trusted to police itself.

`lw-topic.mod` also shows a hand-maintenance artifact in both shells:

```
<!ENTITY % ph "ph | b | i |u | sup | sub" >
```

`|u` with no space. Legal — a DTD does not require whitespace around `|` — and identical in `lw-map.dtd`, so it was copied rather than typed twice. Harmless, and worth naming only as evidence that these files are edited by hand and that a checker, not a reviewer, is what catches the class of thing that is *not* harmless.

XDITA also carries the only real enumerations in the DITA family:

```
scale ( 50|60|70|80|90|100|110|120|140|160|180|200 ) #IMPLIED
frame ( all|bottom|none|sides|top|topbot ) #IMPLIED
expanse ( column|page|spread|textline ) #IMPLIED
scope (local | peer | external) #IMPLIED
```

DITA 1.3 declares almost every attribute `CDATA` and pushes the vocabulary into processing conventions. The lightweight profile, aimed at authors rather than toolchains, puts the values back into the grammar where a validator can check them. That inversion is the point: **the more a vocabulary trusts its processor, the less it declares; the more it trusts its author, the more it declares.** Our subsets sit on the author side — every verdict a declared enumeration, LAW.CORE.3 — and XDITA is the corpus' clearest statement of why that is the right side for a prompt grammar.

### 10.1 `dtds/` is Wireshark, and the DTD is a code generator's input

All twelve files open with the same processing instruction:

```
<?wireshark-protocol
   proto_name="presence"
   description="presence XML doc (RFC 3863)"
   media="application/cpim-pidf+xml"
   hierarchy="yes" ?>
```

Measured: 12 of 12 carry it; 10 carry `hierarchy="yes"`; 3 carry a `media` type. `proto_name` values: `dc`, `itunes`, `list`, `mscml`, `poc-settings`, `presence`, `reginfo`, `rss`, `smil`, `watcherinfo`, `xcap-caps`, `xcap-error`.

These grammars are not validated against. They are read by Wireshark's `xml` dissector generator, which turns each into a protocol dissector; the PI carries the four facts a DTD cannot express — what to call the protocol, what MIME type selects it, whether to build a tree. **The metadata channel is a processing instruction because the grammar has nowhere else to put it.**

Two consequences visible in the files:

Content models are non-deterministic, which XML 1.0 forbids and which a real validator would reject:

```
<!ELEMENT tuple (status? | contact? | note? | timestamp?)* >
<!ELEMENT xcap-caps ((auid?)*, extension?, (namespace?)*) >
<!ELEMENT entity (isb-settings? | am-settings? | ipab-settings? | sss-settings?)* >
```

And two files wrap their declarations in a DOCTYPE inside a file that is named as an external subset:

```
<!-- dc.dtd -->        <!DOCTYPE dc [ … ]>
<!-- itunes.dtd -->    <!DOCTYPE itunes [ … ]>
```

which no XML parser can consume as an external subset. The loose root `WMSDKNS.DTD` does the same:

```
<?xml version="1.0" standalone="yes"?>
<!DOCTYPE document [
<!ELEMENT document (node*)>
    <!ATTLIST document WMSNameSpaceVersion CDATA "2.0">
…
]>
```

Three files in the corpus are shaped this way, all of them consumed by a bespoke reader rather than by a parser.

Parameter-entity use tells the same story: eleven of the twelve `dtds/` files declare **zero** parameter entities. The twelfth is `smil.dtd` — the genuine 1998 W3C SMIL 1.0 DTD, pulled in unmodified except for the PI bolted on top — and it declares 24.

**This is the closest precedent in the corpus to what this repository actually does.** Our `.dtd` files are read by `bin/rot-dtd-commander.mjs` and by `checker/`, not by an XML parser; our subsets carry laws as entity strings that no validator will ever check; the frontmatter beside them is our processing instruction. Wireshark reached the same shape from the same pressure a decade earlier. It is also the corpus' clearest warning: once nothing validates the grammar, nothing catches a non-deterministic content model either, and §10.5 shows what else it stops catching.

### 10.2 `office/`: a flat driver, general entities as namespace URIs, and 42 of 47 datatypes that check nothing

`office.dtd` is 2,193 B and is nothing but fourteen includes in a fixed order:

```
<!ENTITY % dtypes-mod SYSTEM "dtypes.mod">
%dtypes-mod;
<!ENTITY % nmspace-mod SYSTEM "nmspace.mod">
%nmspace-mod;
<!ENTITY % defs-mod SYSTEM "defs.mod">
%defs-mod;
<!ENTITY % office-mod SYSTEM "office.mod">
%office-mod;
… style, meta, script, drawing, text, table, chart, datastyl, form, settings
```

No switch, no redeclaration seam, no public identifiers. The simplest driver in the corpus, and the honest baseline: a modular DTD needs *nothing* except an ordered list of includes. Everything the other families add — switches, extension entities, prefixes, profiles — is bought to enable a customization this one never intends to support.

`nmspace.mod` holds namespace URIs as **general** entities, composed by concatenation:

```
<!ENTITY nOpenOffice "http://openoffice.org/2000">
<!ENTITY nOffice     "&nOpenOffice;/office">
<!ENTITY nStyle      "&nOpenOffice;/style">
<!ENTITY nDraw       "&nOpenOffice;/drawing">
<!ENTITY nSVG        "http://www.w3.org/2000/svg">
```

The inverse of XML Schema's approach (§10.4): general entities building attribute *values*, where XMLSchema.dtd uses parameter entities to build element *names*.

Module shape, measured:

|---|---|---|---|---|
| `text.mod` | 180 | 443 | 12 | 48,205 |
| `drawing.mod` | 60 | **637** | 25 | 45,630 |
| `style.mod` | 26 | 259 | 13 | 23,083 |
| `table.mod` | 79 | 59 | 9 | 19,299 |
| `form.mod` | 27 | 56 | 49 | 14,447 |
| `datastyl.mod` | 26 | 109 | 13 | 11,231 |

| `chart.mod` | 19 | 32 | 2 | 8,956 |

`drawing.mod` carries **637 attribute lists over 60 elements — 10.6 : 1**, the highest ratio anywhere in the corpus, against `table.mod`'s 0.75 : 1. That number is the finding the Graphic family needs stated plainly: **a graphic vocabulary is almost entirely attributes.** Structure says *what kind of thing*; every measurement, transform, fill, stroke, position and unit is an attribute. A geometry grammar that spends its design effort on content models is designing the wrong half.

The element names are the vocabulary the fourth Graphic command must cover:

```
draw:rect draw:line draw:polyline draw:polygon draw:path draw:circle draw:ellipse
draw:connector draw:measure draw:caption draw:contour-polygon draw:contour-path
draw:gradient draw:hatch draw:fill-image draw:transparency draw:marker draw:stroke-dash
draw:g draw:layer draw:layer-set draw:page draw:image draw:object draw:area-rectangle
draw:area-circle draw:area-polygon
dr3d:scene dr3d:light dr3d:cube dr3d:sphere dr3d:extrude dr3d:rotate
```

Three groups worth naming. **`draw:measure`** is a dimension line — the Surveyor's instrument, already a first-class element in a shipping office suite. **`dr3d:extrude` and `dr3d:rotate`** are the two classical solid constructions (extrusion and revolution) declared as elements beside the primitives — the Architect's operations. **`draw:contour-polygon` / `draw:contour-path`** are traced outlines over a raster — the Renovator's operation, taking an existing image and deriving geometry from it. The three bands the brief names map onto three groups of elements this vocabulary already separates.

`dtypes.mod` is the file to read against `tei.dtd`'s `teidata.*` (§4). 47 parameter entities: **35 expand to exactly `CDATA`, 7 to `#PCDATA`, 2 are real enumerations** (`valueType`, `anchorType`), 2 are element-name lists (`shape`, `shapes`), 1 is an attribute fragment (`control-id`).

```
<!ENTITY % length				"CDATA">
<!ENTITY % positiveLength		"CDATA">
<!ENTITY % nonNegativeLength	"CDATA">
<!ENTITY % lengthOrPercentage	"CDATA">
<!ENTITY % coordinate			"CDATA">   <!-- "an svg coordinate in different distance formats" -->
<!ENTITY % percentage 			"CDATA">
<!ENTITY % color				"CDATA">   <!-- "a color value having the format #rrggbb" -->
<!ENTITY % floatOrPercentage	"CDATA">
```

Every dimensional type the Graphic suite needs is here, named, documented in a comment — and **none of them constrains anything**. TEI: 64 `teidata.*`, 63 CDATA, one enumeration. OpenOffice: 47 types, 42 carrying no constraint. Two unrelated projects, same ratio, same conclusion:

> **A DTD datatype library is documentation wearing a validator's name.**

For `geometry.dtd` this settles the deferred question about pre-built profiles versus a driver only, at least partially: whichever we ship, **the DTD cannot check a coordinate, an angle, a ratio or a colour.** The names belong in the grammar for provenance and readability; the checking belongs in `checker/`, which is where this repository already puts it. Declaring `%angle;` and believing it validated would be the single most expensive mistake available in this design.

### 10.3 `daisy/`: three revisions, 82 elements, and a count the prose got wrong for five years

Eleven grammar files, 402,044 B, dominated by three revisions of one DTD:

| file | ELEMENT | ATTLIST | ENTITY % | bytes |
|---|---|---|---|---|
| `dtbook-2005-1.dtd` | 82 | 82 | 54 | 97,726 |
| `dtbook-2005-2.dtd` | 82 | 82 | 59 | 103,636 |
| `dtbook-2005-3.dtd` | 82 | 82 | 58 | 105,645 |

Element sets compared by name: **identical across all three.** ATTLIST count identical. The entire published difference between three NISO revisions spanning 2005-06-26 to 2007-12-19 lives in the parameter-entity layer:

```
2005-1 -> 2005-2   added: externalFlow, externalNamespaces   removed: StyleSheet
2005-2 -> 2005-3   added: (none)                             removed: dtbookblock
```

Three revisions, five parameter-entity names changed, zero elements changed. The PE layer is where a mature DTD versions, because it is the only layer a document does not see.

Then the defect. Every one of the three files states in its own prose:

```
Dtbook-2005-3 has 83 element types. It shares 46 element types with the …
```

and every one of the three declares **82**. Verified three ways: 82 `<!ELEMENT` tokens, 82 unique element names, zero declarations with the name on a following line, zero commented-out declarations. The sentence was written once, copied through two revisions, and never re-measured across five years of committee work.

This is precisely the drift `checker/readme-index.mjs` exists to catch — a documented count disagreeing with the artifacts it counts. Finding it in a NISO standard is the argument for keeping that checker: the number in the prose is the *first* thing to rot, because nothing recomputes it.

The same files show the anti-pattern our release law targets. `2005-3` appears **21 times** in `dtbook-2005-3.dtd` — in the filename, the public identifier, the system identifier twice, the documentation references `[DTBOOKV20053DTD]` and `[DTBOOKV20053DOC]`, and a sentence reading `distinguished by the string "2005-2"`. Twenty-one hand-typed occurrences of a version, in one file, per revision. `lib/amplify.mjs recognize` computing the version and `checker/release-notes.mjs --versions` refusing a disagreement is the answer to exactly this file.

The rest of `daisy`: `ncx-2005-1.dtd` (navigation control), `dtbsmil-2005-1/2.dtd` (14 elements each), `bookmark-2005-1.dtd` (15), `distInfo-2005-1.dtd` (12), `resource-2005-1.dtd` (9), `oebpkg12.dtd`, and `oeb12.ent` — 254 general entity declarations of named characters, the OEB mnemonic set, the same species as MathML's ISO sets (§5) and JATS's (§7). `ncx-2005-1.dtd`'s header is a 30-line dated change log naming each change and its issue number, the DocBook/JATS convention (§6, §7).

### 10.4 The ten loose roots

```
   287 B  ModularMonet.dtd      4 elements, 3 attlists, 0 PE
   498 B  WMSDKNS.DTD           DOCTYPE-wrapped, 2 elements, 5 attlists
   504 B  gdb-syscalls.dtd      2 elements
 2,344 B  language.dtd          GtkSourceView syntax definitions
 2,802 B  krita.dtd             the KRA image format
 4,614 B  edoc.dtd              Erlang EDoc
 6,179 B  datatypes2004.dtd     XML Schema Part 2, as a DTD
 6,357 B  datatypes.dtd         XML Schema Part 2, as a DTD
16,013 B  XMLSchema2004.dtd     XML Schema Part 1, as a DTD
16,075 B  XMLSchema.dtd         XML Schema Part 1, as a DTD
```

**`XMLSchema.dtd` — a schema language described in the schema language it replaced.** The prefix technique in its purest form:

```
<!ENTITY % p 'xs:'>   <!-- can be overriden in the internal subset of a
                           schema document to establish a different
                           namespace prefix -->
<!ENTITY % s ':xs'>   <!-- if %p is defined (e.g. as foo:) then you must
                           also define %s as the suffix for the appropriate
                           namespace declaration (e.g. :foo) -->
<!ENTITY % nds 'xmlns%s;'>
<!ENTITY % schema "%p;schema">
<!ENTITY % complexType "%p;complexType">
…
```

SVG and MathML put the prefix redeclaration in a *driver file* (§1, §5); DITA puts it in an 18-line ditadriver (§8.7); XMLSchema.dtd puts it **in the internal subset of the instance itself**. `%nds;` builds the name of the namespace-declaration attribute out of a parameter entity — the technique carried one step further than anywhere else in the corpus.

Then twenty-odd empty seams in a single block:

```
<!-- Customisation entities for the ATTLIST of each element type.
     Define one of these if your schema takes advantage of the
     anyAttribute='##other' in the schema for schemas -->
<!ENTITY % schemaAttrs ''>
<!ENTITY % complexTypeAttrs ''>
<!ENTITY % elementAttrs ''>
…
```

One empty extension entity per element type, all declared together, each named `<element>Attrs`. The most regular extension-point scheme in the corpus — SVG's `SVG.X.extra.class`, TEI's `x.model.X` and DocBook's `local.X.class` are the same idea with less uniform coverage.

And the header, which is the most honest sentence in the corpus:

```
<!-- Note this DTD is NOT normative, or even definitive. -->
<!-- prose copy in the structures REC is the definitive version -->
…
<!-- any XML document which is not valid per this DTD given redefinitions
     in its internal subset of the 'p' and 's' parameter entities below
     appropriate to its namespace declaration of the XML Schema namespace
     is almost certainly not a valid schema. -->
```

"almost certainly not". The W3C shipped a DTD for its own schema language and stated in the file that it is a heuristic, not a decision procedure. Every grammar in this corpus is a filter; this is the only one that says so.

`XMLSchema.dtd` and `XMLSchema2004.dtd` differ by 12 diff lines — a CVS `$Id$` and comment rewrapping. `datatypes.dtd` and `datatypes2004.dtd` differ by 160, and the substantive difference is the facet names:

```
datatypes.dtd      <!ENTITY % totalDigits "%p;totalDigits">
                   <!ENTITY % fractionDigits "%p;fractionDigits">
datatypes2004.dtd  <!ENTITY % precision "%p;precision">
                   <!ENTITY % scale "%p;scale">
```

The `$Id$` lines read `datatypes.dtd,v 1.23 2001/03/16` and `datatypes.dtd,v 1.1 2004/10/21`. The file with the later date carries the *earlier* facet names, so the `2004` suffix names when the copy was cut, not which revision it holds. Recorded as measured; the corpus does not say which the author intended to ship, and guessing would be the defect §0 forbids.

**`krita.dtd`** is the loose root closest to the Graphic family's subject — the KRA raster format:

```
<!ELEMENT DOC (IMAGE)>
<!ATTLIST DOC editor CDATA 'krita' depth CDATA #REQUIRED syntaxVersion CDATA #REQUIRED>
<!ELEMENT IMAGE (LAYERS)>
<!ATTLIST IMAGE name … mime … width … height … x-res … y-res … profile … colorspacename …>
<!ELEMENT LAYERS (layer)+>
<!ELEMENT layer (LAYERS)?>
<!ATTLIST layer name x y width height opacity visible linked colorspacename profile
                filename layertype CDATA "paintlayer" filtername CDATA "" filterversion CDATA "">
```

`<!ELEMENT layer (LAYERS)?>` inside `<!ELEMENT LAYERS (layer)+>` — recursion, which is how a layer group nests. Every geometric attribute is CDATA, again. Obsolete attributes are marked *in comments* (`width: The layer's width in pixels OBSOLETE`) and left `#IMPLIED` in the declaration — append-only enforced by prose rather than by structure, the weakest form of the discipline DITA enforces at file level (§9.2).

`edoc.dtd` is the other one worth naming: a documentation grammar carrying a full recursive type algebra —

```
<!ELEMENT type (typevar | atom | integer | float | nil | list | tuple |
                fun | record | abstype | union)>
<!ELEMENT union (typevar | atom | … | map | abstype)+>
<!ELEMENT fun (argtypes, type)>
<!ELEMENT list (type)>
<!ELEMENT tuple (type*)>
<!ELEMENT map (map_field)*>
<!ELEMENT map_field (type, type)>
```

A type system expressed as mutually recursive content models. Direct precedent for the codebase family: a DTD *can* carry a recursive algebra when the thing being described is structure rather than measurement. Which sharpens §10.2's conclusion — DTDs are good at shape and useless at magnitude.

### 10.5 Three dangling references, found by reading, invisible to every validator

The reason this study was done verbatim rather than by census alone:

| where | shape | detail |
|---|---|---|
| `lw-topic.dtd`, `lw-map.dtd` (XDITA) | **orphan** — declared, never referenced | `<!ENTITY excluded-domains " ">` declared twice, documented in four lines of prose with a naming convention, expanded nowhere in any of the five grammar files |
| `krita.dtd` | **dangling** — referenced, never declared | `<!ELEMENT FILTERCONFIG (filterconfig)>`; `filterconfig` appears once in the file, in that content model, and has no declaration |
| `office/dtypes.mod` | **dangling** — referenced, never declared | `draw:custom-shape` appears once in the whole `office/` tree, inside `<!ENTITY % shape …>`, and has no `<!ELEMENT`; every content model that expands `%shape;` therefore names an undeclared element type |

Three unrelated shipped grammars — OASIS, KDE, OpenOffice — two defect shapes, and **not one of them is reported by parsing the DTD.** An orphan declaration is legal. A dangling reference in a content model is legal until an instance uses the element, and then the error is reported against the *document*, blaming the author for the grammar's defect.

The only instrument that finds either is a census of declarations against references — a program, not a schema. That is what `dtd-contract-auditor` does and why it must stay a program. It is also the answer to a question 9.0.0 has to settle: `cc-chain.dtd` cannot be trusted to police the chain it declares, because the class of error a chain grammar is most likely to have — a band declaring a successor that does not exist — is exactly a dangling reference, and exactly the class no validator reports.

The corresponding rule for our own release: **every entity the subsets declare must be spent somewhere the checker can see, and every name a body references must resolve to a declaration.** Both directions, measured, every pass. Three standards bodies did not do this and each shipped a defect that has outlived its maintainers.

### 11.5 A measured defect: the README renders families in the wrong order

`checker/readme-index.mjs:31` declares `FAMILIES` with an explicitly ordered `members` array per family. `collect()` builds the command list with one global alphabetical sort:

```js
const commands = readdirSync(join(root, 'commands')).filter((f) => f.endsWith('.md')).sort().map(...)
```

and both render paths (`:160` and `:302`) then do `rows: commands.filter((c) => c.family === f.id)`. The filter preserves the alphabetical order and the declared order is never consulted. Measured in the generated artifacts:

| family | declared in `FAMILIES` | rendered in `docs/family-*.svg` | |
|---|---|---|---|
| `geometry` | surveyor, architect, renovator | **architect, renovator, surveyor** | wrong |
| `lists` | file-black, code-black, file-gray, code-gray, file-white, code-white, starlist, starlist-manager | **code-black, code-gray, code-white, file-black, file-gray, file-white, starlist, starlist-manager** | wrong |
| `growth` | amplify, enhance, overhaul | amplify, enhance, overhaul | correct by coincidence |

`growth` is right only because its ladder order and its alphabetical order happen to agree. `geometry` loses the band order the brief names explicitly. `lists` loses the black-grey-white progression, scrambling it into code-then-file — which inverts LAW.LIST.2's own statement that scope is the axis and colour the progression.

The README's *prose* at line 461 already reads correctly ("The surveyor measures… the architect declares… the renovator changes"), so the defect is only in the generated index and its SVGs — which is the worse place, because prose is read once and the index is the thing a reader navigates by.

### 11.7 The open decision, now answerable

§0 recorded a design question deferred without an answer: whether `geometry.dtd` ships **pre-built profiles** or **only a driver with switches**. The corpus now answers the half of it that is answerable by evidence.

- MathML ships a driver *and* an 18-line pre-built profile (`mathml2.dtd`, §5) — the profile exists because a named, citable configuration is what a document's DOCTYPE points at.
- DocBook ships one driver per dialect plus `dbsvg.dtd` as a pre-built combination, and needs `configerror.txt` to make the illegal combination fail (§6).
- DITA ships **only** shells — 27 of them, each a pre-built profile, and no switch anywhere (§8.1). Its "driver" and its "profile" are the same artifact.
- XDITA ships two shells with the customization points as commented-out declarations (§9.4).

The pattern across four families: **a switch is for the grammar's own maintainers; a profile is for the people who point a document at it.** A family with many consumers ships profiles; a family whose consumers are all in-house ships switches. Our consumers are commands in this repository — and each command already *is* a profile, because the installer inlines a subset into its DOCTYPE.

So the answer the corpus supports is: keep the driver with switches as the source of truth, and treat each command's inlined subset as its pre-built profile — which is what the installer already does. What is missing is DITA's discipline of naming the configuration *in the artifact*: `domains CDATA "&included-domains;"` (§8.4). The chain's handed-on artifact should carry the bands that produced it the same way, so the next command in the chain reads the configuration rather than re-deriving it.

That is not a decision the study can take alone — it changes what `cc-chain.dtd` declares — but the deferred question is no longer open for lack of evidence. It is now a choice with a measured precedent on each side, and the precedent for "profiles for outside consumers, switches for maintainers" is the stronger one, four families to zero.

## 12. What the study decides, and one correction to the 9.0.0 plan

`artifacts/research/2026-09-06-9-0-0-interoperable-commander-deep-dive.md` is the plan of record and stands. This section supplies the corpus evidence behind each of its open items and corrects one measurement.

### 12.1 The correction: the wrong order is ours, not the harness's

The prior deep dive recorded:

> The alphabetical order architect, renovator, surveyor comes from the harness skill list, which sorts by name.

Measured today, that is only half of it. `docs/family-the-graphic-and-geometric-suite.svg` — a file this repository generates and commits — renders:

```
codebase-architect
codebase-renovator
codebase-surveyor
```

The cause is in our own code, `checker/readme-index.mjs`: `collect()` sorts `readdirSync('commands')` alphabetically once, and both render paths filter that single ordered list per family, never consulting the `members` array that already declares the right order at line 31. The same defect scrambles the `lists` family's black-grey-white progression into code-then-file (§11.5).

This matters for the plan because the prior mitigation — "the README row and the chain runner carry the order; renaming is the operator's call" — treats the order as unfixable inside the repo. It is fixable, in one function, and the fix corrects the plate, the row and a second family at once. **No rename is needed** and the operator's answer at intake (Architect and Renovator mirror the real professions; the Surveyor is the desk-bound checker who confirms everything is makeable "before sending a Telegram to the Construction Firm") stands undisturbed.

### 12.2 The eight decisions the corpus settles

**1. `cc-chain.dtd` is flat.** `ditaval.dtd` (§8.8) is DITA's own control language: 9 declarations, no parameter entity, no `class`, no `domains`, no module, and its only enumeration `(flag|include|exclude|passthrough)` is real where the content vocabulary is CDATA everywhere. DITA had every extensibility tool loaded and used none of them for the file that controls processing. The chain grammar declares a root, an ordered band list, one intake, one gate, and `--no-gate` as a token — enumerations and `#REQUIRED`, not a parameterised module. Nobody specialises a build file.

**2. The chained artifact carries its own configuration.** `domains CDATA "&included-domains;"` (§8.4) puts the grammar's assembled configuration into every instance by attribute defaulting, so a processor holding only the document knows what produced it. A band's artifact handed on as the next band's user-args must carry the bands that produced it the same way, rather than the next band re-deriving it. This is also what makes "each command declaring its successor or none" checkable from the artifact rather than only from the DTD.

**3. Configuration by redeclaration, not by switch, wherever a new subset is written.** DITA: 0 conditional sections across 130 grammar files, three major versions, twelve years (§8.1, §9). JATS: 0 across 90 (§7). Both are the most heavily specialised vocabularies in the corpus. A switch answers "is this module present?"; a redeclaration answers "what does this name expand to?", which subsumes it and adds narrowing and emptying. `geometry.dtd`'s three band switches stay — LAW.GEOM.6 depends on them and they work — but the extended ladder does not need more of them.

**4. The ladder extends by addition only, and never renumbers.** DITA 1.1 → 1.2 → 1.3: every grammar file basename survives, 36 → 97 → 159, zero renames, zero deletions, one parameter entity removed in a 700-line module across a major version (§9.2). That is LAW.REC.2 held by a committee for twelve years. The 52 existing rungs keep their numbers and their wording; the general graphical ladder is appended above 52, and `GEOM.instrumented` gains entries without any rung moving.

**5. The figure vocabulary must grow toward attributes, not elements.** `drawing.mod`: 60 elements, **637 attribute lists**, ratio 10.6 : 1, against `table.mod`'s 0.75 : 1 (§10.2). A graphic vocabulary is almost entirely attributes. `cc-figure.dtd`'s four shapes with 4–5 attributes each is a diagram vocabulary. The generator needs the shapes the corpus names — and the three bands map onto three groups OpenOffice already separates: `draw:measure` (the Surveyor's dimension line), `dr3d:extrude` / `dr3d:rotate` (the Architect's solid constructions), `draw:contour-polygon` / `draw:contour-path` (the Renovator's tracing of what already exists).

**6. The DTD cannot check a coordinate, and must not pretend to.** TEI: 64 `teidata.*`, 63 CDATA, one real enumeration (§4). OpenOffice `dtypes.mod`: 47 datatypes, 42 carrying no constraint, including every dimensional type the Graphic suite needs — `length`, `positiveLength`, `nonNegativeLength`, `coordinate`, `percentage`, `color`, `floatOrPercentage` (§10.2). Two unrelated projects, same ratio. Declaring `%angle;` and believing it validated is the single most expensive available mistake in this design. The names go in the grammar for provenance; the checking goes in `checker/`, which is where this repository already puts it.

**7. The extension seam ships as commented-out declarations.** XDITA writes each supported constraint into the shell as an inert comment the user uncomments, with the naming convention for the resulting constraint spelled out beside it (§9.4). SVG, TEI and DocBook publish an empty entity and leave the author to find its name in documentation. The generated schematics of `create-prompt-<schematic>-dtd` should carry their customization points the same way: the redeclaration, commented, with the law that governs it on the line above.

**8. The audit stays a program, in both directions.** Three shipped grammars, three unrelated standards bodies, two defect shapes, none reported by any parser (§10.5): XDITA's `excluded-domains` declared twice and referenced nowhere; `krita.dtd`'s `FILTERCONFIG (filterconfig)` naming an element that does not exist; OpenOffice's `%shape;` naming `draw:custom-shape`, which has no declaration anywhere in its tree. Add the fourth, ours by construction: `dtbook-2005-1/2/3` each state "has 83 element types" and each declare 82, unchanged across five years (§10.3). A chain grammar's most likely error — a band declaring a successor that does not exist — is exactly a dangling reference, and exactly the class nothing validates. `cc-chain.dtd` cannot police the chain it declares; `dtd-contract-auditor` and `checker/readme-index.mjs` must.

### 12.3 The anti-pattern the release closes

`dtbook-2005-3.dtd` contains the string `2005-3` **21 times** — filename, public identifier, system identifier twice, two documentation reference keys, and a sentence reading `distinguished by the string "2005-2"` (§10.3). Three revisions, each hand-typed, each carrying a prose element count that was wrong in all three.
